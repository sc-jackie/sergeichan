    Compound Engineering — Capture & Refresh¶

    Coordinate documentation of solved problems and maintain docs/solutions/ quality over time. Two modes:

    • Capture (default) — document a recently solved problem or durable vocabulary into docs/solutions/ or CONCEPTS.md. Use after work ships.
    • Refresh — audit existing learnings for staleness, overlap, or drift against the current codebase. Use periodically to maintain knowledge quality.

    Mode Detection¶

    Check $ARGUMENTS for a mode token — either mode:headless or a scope hint matching refresh patterns. Scope hints that narrow docs/solutions/ or query its metadata (directory names, module tags, filenames) indicate refresh mode; otherwise default to capture mode.

    Indicator Mode
    No arguments, or [context] describing a solved problem + optional mode:headless Capture (document the solution)
    Argument matches a docs/solutions/ directory, module name, or file slug (or refresh learnings, audit stale, ce-compound-refresh) + optional mode:headless Refresh (audit and maintain)
    CONCEPTS.md bootstrap (or build concept map) without a problem context Refresh: asks whether to bootstrap the concept map or run a refresh cycle

    Once mode is determined, check for mode:headless token and strip it from arguments before proceeding. Headless mode applies throughout the chosen workflow.

    Shared Interaction Principles¶

    Headless Mode¶

    • No user interaction. Never pause for input, never present options, never ask questions.
    • Process in scope fully. Run all unambiguous actions (Keep, Update, Consolidate, auto-Delete, Replace).
    • Ambiguous cases → stale-mark. If classification is uncertain, mark the file with status: stale, stale_reason, and stale_date in frontmatter.
    • Apply edits silently. Vocabulary capture and instruction-file edits are side effects, not decisions.
    • Generate a report. Output structured terminal report at the end (see Output Format).

    Interactive Mode¶

    • Ask one question at a time using platform blocking tools (AskUserQuestion in Claude Code, request_user_input in Codex, ask_question in Antigravity, ask_user in Pi).
    • Fall back to numbered options in plain text only when no blocking tool exists.
    • Lead with recommendations and one-sentence rationale.
    • For capture mode: ask Full vs Lightweight, then ask about session history (Full only), then ask for consent on Discoverability Check edits.
    • For refresh mode: ask for scope, then present recommendations per artifact, handling ambiguous cases with user input.

    Shared Materials¶

    Frontmatter Schema & YAML Safety¶

    Read references/schema.yaml for canonical frontmatter fields and enum values. Read references/yaml-schema.md for category mapping, YAML safety rules (unquoted # silently truncates, unquoted : can confuse YAML parsers), and array-item quoting. Both modes apply these rules consistently.

    CONCEPTS.md Handling¶

    A shared vocabulary file, seeded and refined across both capture and refresh runs:

    1. Capture mode (Phase 2.4): When a new learning surfaces qualifying domain terms, add them to an existing CONCEPTS.md or create/seed one if absent. Hold the qualifying bar conservatively for borderline terms at creation; updates follow normal criteria. Seed the learning's area only, not repo-wide.

    2. Refresh mode (Phase 4.5): Aggregate domain terms flagged across the learnings in scope. If CONCEPTS.md exists, add missing terms and reconcile in-scope core nouns from the declared model. If absent and terms qualified, bootstrap and seed. Apply edits silently in all modes.

    3. Discoverability: After creating/updating CONCEPTS.md, check whether instruction files (AGENTS.md / CLAUDE.md) surface it. (See Discoverability Check below.) Bootstrap always includes this step.

    When bootstrapping, use this preamble:

    Shared domain vocabulary for this project — entities, named processes, and status concepts with project-specific meaning. Seeded with core domain vocabulary, then accretes as ce-compound and ce-compound-refresh process learnings; direct edits are fine. Glossary only, not a spec or catch-all.

    Discoverability Check¶

    After the learning or refresh is complete, verify that instruction files would lead agents to docs/solutions/ and (if it exists) CONCEPTS.md.

    Procedure (identical in both modes):

    1. Identify root-level instruction files (AGENTS.md, CLAUDE.md, or both). Read the substantive one (if one is a shim including the other, that's the target).
    2. Assess whether an agent would learn: (a) that a searchable knowledge store exists; (b) enough about its structure (categories, YAML fields); (c) when to search it.
    3. If not surfaced, draft a small addition matching the file's existing style. A one-liner in an existing section beats a new headed section.
    4. Capture (Interactive): Show the proposed change and ask for consent using the blocking question tool. Apply silently in lightweight mode.
    5. Refresh (Interactive): Show the proposed change and ask using the blocking question tool. Apply silently.
    6. All Headless modes: Include the recommendation in the terminal report; do not edit instruction files.

    Frontmatter Validation¶

    In Phase 2 (capture) and Phase 4 (refresh), after writing the doc, validate YAML parser-safety using the bundled script:

    if [ -n "${CLAUDE_SKILL_DIR}" ] && [ -f "${CLAUDE_SKILL_DIR}/scripts/validate-frontmatter.py" ]; then
  python3 "${CLAUDE_SKILL_DIR}/scripts/validate-frontmatter.py" <output-path>
else
  # Manual check: opening/closing `---`, no unquoted ` #` or `: ` in scalar top-level values
  true
fi

    Capture Mode¶

    Use when: Documenting a recently solved problem or durable project vocabulary. Default mode.

    Invocation¶

    /jos-compound                     # Document the most recent fix
/jos-compound [context]           # Provide context hint
/jos-compound mode:headless       # Non-interactive (for automations)
/jos-compound mode:headless [ctx] # Non-interactive with context

    Preconditions (Advisory)¶

    • Problem has been solved and verified working
    • Non-trivial (not simple typo or obvious error)

    Pre-Execution¶

    Git context (pre-resolved): - Branch: !git rev-parse --abbrev-ref HEAD 2>/dev/null || true - Repo root: !git rev-parse --show-toplevel 2>/dev/null || pwd

    Auto memory (Claude Code only): Before Phase 1, scan the auto-memory block injected into your system prompt for relevant notes related to the problem being documented. If found, prepare an excerpt and pass it to Phase 1 subagents. Tag memory-sourced content in the final doc with "(auto memory [claude])".

    Phase 0: Mode Selection & Execution Route¶

    Headless mode: Skip interactive questions, run Full Mode without session history, apply the Discoverability Check edit silently if a gap exists, skip Phase 3 specialized reviews. Emit structured terminal report and end the turn.

    Interactive mode (before Phase 1): Present two options using the blocking question tool:

    1. Full (recommended) — the complete workflow. Researches, cross-references,
   and reviews your solution to produce documentation that compounds your
   team's knowledge.
2. Lightweight — same documentation, single pass. Faster and uses fewer
   tokens, but won't detect duplicates or cross-reference existing docs.
   Best for simple fixes or long sessions nearing context limits.

    If user chooses Full, ask one follow-up: "Would you also like to search your [harness name] session history for relevant knowledge? This adds time and token usage." (Session history enabled only on "yes".)

    Phase 1: Research (Full Mode Only)¶

    Launch three research subagents in parallel (background) to investigate the problem space. Each writes its full output to a per-run scratch artifact under /tmp/compound-engineering/jos-compound/{run_id}/ and returns only the artifact path.

    Run ID: Generate once at start: RUN_ID=$(date +%Y%m%d-%H%M%S)-$(head -c4 /dev/urandom | od -An -tx1 | tr -d ' '). Artifacts:

    • Context Analyzer → context.json (frontmatter skeleton, category, filename, track)
    • Solution Extractor → solution.md (full doc body prose, track-appropriate sections)
    • Related Docs Finder → related.json (links, related learnings, overlap assessment)

    Each subagent must confirm the artifact write succeeded (file exists and is non-empty) before returning only the artifact path. If write fails, return the full output inline instead (no path).

    After parallel block launches, optionally run session-history synthesis (if user opted in): Discover sessions on the current branch from the past 7 days, extract relevant context using bundled scripts under scripts/session-history/, synthesize via a subagent seeded with references/agents/session-historian.md, and write findings to /tmp/compound-engineering/jos-compound/{run_id}/session-history.md. Platform-specific: if ${CLAUDE_SKILL_DIR} does not resolve or scripts are missing, skip with a visible note.

    Phase 2: Assembly & Write¶

    1. Collect Phase 1 artifacts: Read context.json, solution.md, related.json, and (if session history ran) session-history.md from /tmp/compound-engineering/jos-compound/{run_id}/. Artifact is authoritative; fall back to inline return only if artifact is absent or empty.

    2. Overlap check: From Related Docs Finder, check overlap assessment:

    3. High (existing doc covers same problem, root cause, solution) → Update the existing doc with fresher context, new examples, updated references. Preserve file path and frontmatter structure. Add last_updated: YYYY-MM-DD field.
    4. Moderate (same area, different angle) → Create the new doc, flag for Phase 2.5 consolidation review.

    5. Low or none → Create new doc.

    6. Incorporate session history (if available): Fold dead ends into "What Didn't Work" (bug track) or "Context" (knowledge track). Tag with "(session history)".

    7. Assemble doc: Read assets/resolution-template.md for section structure. For new docs, use the template section order unless the user explicitly asks otherwise. Merge collected pieces into complete markdown.

    8. Create directory and write: mkdir -p docs/solutions/[category]/ and write either the new docs/solutions/[category]/[filename].md or update the existing doc.

    9. Validate frontmatter: See Frontmatter Validation above.

    Phase 2.4: Vocabulary Capture (applies to both Full and Lightweight)¶

    First, read references/concepts-vocabulary.md unconditionally. Do not pre-judge from memory.

    Scan the new doc and the surrounding conversation for qualifying domain terms. If CONCEPTS.md exists, add missing terms and refine existing entries when new precision surfaced. If absent and at least one term qualifies, create and seed it.

    At creation, hold the qualifying bar conservatively for borderline terms. Seed the learning's area only (modules and domain the fix touched), not repo-wide.

    Record the outcome explicitly (e.g., "Vocabulary: 1 entry added" or "scanned, no qualifying terms"). Do not silently skip.

    Apply edits silently in every mode — no user prompt.

    Phase 2.5: Selective Refresh Check¶

    After writing, assess whether older learnings should be refreshed. Invoke ce-compound-refresh (or recommend it) when:

    • A related doc recommends an approach the new fix contradicts
    • The new fix clearly supersedes an older solution
    • Work involved refactoring, migration, or dependency upgrade that invalidates older references
    • A pattern doc looks overly broad or outdated
    • Related Docs Finder surfaced high-confidence refresh candidates or moderate overlap

    Do not invoke without evidence or broadening into a large sweep from a lightweight session.

    Phase 3: Optional Enhancement (Full Mode Only, Not Headless)¶

    Based on problem type, optionally dispatch subagents seeded with local prompts from references/agents/ to review the documentation for depth and edge cases (performance-oracle, security-sentinel, data-integrity-guardian, or code-simplification review). Do not mutate product code.

    Lightweight Mode¶

    Single-pass alternative: orchestrator performs all work sequentially without parallel subagents.

    1. Extract from conversation + auto-memory
    2. Classify: read schema and yaml-schema, determine track, category, filename
    3. Write minimal doc using assets/resolution-template.md
    4. Vocabulary capture (update-only): if CONCEPTS.md exists, add missing/refine entries. Do not bootstrap/seed.
    5. Skip Phase 3 specialized reviews

    Output: 

    ✓ Documentation complete (lightweight mode)

File created:
- docs/solutions/[category]/[filename].md

[If discoverability gap found:]
Tip: Your AGENTS.md/CLAUDE.md doesn't surface docs/solutions/ —
a brief mention helps all agents discover these learnings.

Note: This was created in lightweight mode. For richer documentation
(cross-references, detailed prevention strategies, specialized reviews),
re-run /jos-compound in a fresh session.

    Refresh Mode¶

    Use when: Auditing existing learnings against the current codebase to catch staleness, overlap, or drift. Periodic maintenance.

    Invocation¶

    /jos-compound refresh                           # Audit all of docs/solutions/
/jos-compound refresh auth                      # Audit docs related to auth
/jos-compound refresh [directory/file/module]   # Narrow to scope hint
/jos-compound refresh mode:headless             # Headless audit, all scope
/jos-compound refresh [scope] mode:headless     # Headless audit, scoped

    Phase 0: Route by Scope¶

    Before investigation:

    1. Discover candidate artifacts under docs/solutions/ (exclude README.md and _archived/).
    2. Estimate scope: Is this 1-2 files, ~8 docs, or 9+ (broad sweep)?
    3. Route interaction:
    4. Focused (1-2 files or user named a specific doc) → Investigate directly, present recommendation.
    5. Batch (~8 independent docs) → Investigate first, present grouped recommendations.
    6. Broad (9+ docs, ambiguous, or repo-wide sweep) → Lightweight triage first, recommend starting area, then investigate in batches.

    Broad-scope triage: Read frontmatter of all candidates, group by module/component/category. Identify high-impact clusters (dense modules with cross-references and stale references). Recommend starting with the cluster with most references broken. (In headless, skip recommendation and process all clusters by impact order.)

    Phase 1: Investigate Learnings¶

    For each learning in scope, read it and cross-reference against the codebase. Assess staleness across five dimensions:

    • References — do file paths, class names, modules still exist or have they moved/been renamed?
    • Solution — does the recommended fix still match how code actually works today?
    • Code examples — do snippets still reflect the current implementation?
    • Related docs — are cross-referenced learnings and patterns still present and consistent?
    • Auto memory (Claude Code only) — does the auto-memory block in your system prompt contain entries in the same domain? If yes and the approach differs from the learning, flag as drift signal.
    • Overlap — note other docs in scope covering the same problem domain. Record which dimensions overlap and which doc appears broader/more current.
    • Vocabulary — note domain terms the learning cites. Flag whether they appear in CONCEPTS.md and whether definitions still match current code usage.

    Drift classification — Update vs Replace:

    • Update: File paths moved, classes renamed, links broke, metadata drifted, but the core recommended approach is still how code works. → Apply evidence-backed in-place edits.
    • Replace: Recommended solution conflicts with current code, architecture changed, or pattern is no longer preferred. → Write a successor via subagent (not inline).

    If you find yourself rewriting the solution section, stop — that is Replace, not Update.

    Judgment guidelines:

    1. Contradiction = strong Replace signal. Learning actively misleading.
    2. Age alone is not a stale signal. A 2-year-old learning matching current code is fine.
    3. Check for successors before deleting. Prefer Replace over Delete when evidence exists.

    Phase 1.5: Investigate Pattern Docs¶

    After reviewing learnings, check pattern docs under docs/solutions/patterns/. A stale pattern is more dangerous than a stale individual learning.

    Phase 1.75: Document-Set Analysis¶

    Step back and evaluate the document set as a whole for contradictions, overlaps, and supersession.

    Overlap detection: Compare docs sharing module/component/tags across problem statement, solution shape, referenced files, prevention rules, root cause. High overlap across 3+ dimensions is a strong Consolidate signal.

    Supersession signals: Newer doc covers same files and workflow but broader context; older doc is narrow precursor; newer doc has better examples. → Consolidation candidate.

    Canonical doc identification: For each topic cluster, identify which doc is the authoritative source of truth. Other docs are either Distinct (independent retrieval value), Subsumed (unique content fits as section in canonical doc), or Redundant (adds nothing new).

    Retrieval-value test: Would separate docs improve discoverability or just create drift risk? Separate only if they cover genuinely different sub-problems or target different contexts.

    Cross-doc conflicts: "Always X" vs "Avoid X" for the same problem. Contradictions are more urgent than individual staleness.

    Phase 2: Classify the Maintenance Action¶

    Assign one of five outcomes:

    Action When Default
    Keep Still accurate and useful No edit; report reviewed and trustworthy
    Update Core solution valid, references drifted In-place edits (paths, links, snippets, metadata)
    Consolidate Two docs overlap heavily, both correct Merge unique content into canonical, delete subsumed
    Replace Core guidance now misleading Write successor via subagent, then delete old
    Delete No longer useful, code gone, fully redundant Delete the file (git history preserves it)

    Consolidate vs Delete: If subsumed doc has unique content worth preserving, consolidate first; if it adds nothing, delete.

    Replace: Use only when you understand both what the old learning recommended AND what the current approach is. If evidence is insufficient, mark as stale instead.

    Delete: Only after checking for inbound links. Classify citations as decorative (see-also pointers, safe to delete) vs substantive (citing doc relies on cited doc, signal Replace instead). Auto-delete only when: implementation is gone, problem domain is gone, and citations are absent/decorative.

    Phase 3: Ask for Decisions (Interactive Mode Only)¶

    Headless: Skip entirely. Proceed to Phase 4; execute unambiguous actions, mark ambiguous as stale.

    Interactive: Ask questions one at a time using blocking tools. Present choices only when the right action is genuinely ambiguous (e.g., Update vs Replace vs Consolidate, or Delete with non-trivial evidence). For obvious Keeps and Updates, apply directly without asking.

    Phase 4: Execute Chosen Action¶

    • Keep — No file edit; summarize why trustworthy.
    • Update — In-place edits when solution is substantively correct.
    • Consolidate — Merge overlapping docs, delete subsumed, update cross-references. Orchestrator handles directly.
    • Replace — Write successor learning via subagent (pass documentation contract files), validate frontmatter, delete old. If evidence insufficient, mark stale.
    • Delete — Final inbound-link check, then remove. Reclassify if substantive citations surface.

    Phase 4.5: Vocabulary Capture (Refresh-Specific)¶

    After per-learning actions:

    1. Read references/concepts-vocabulary.md unconditionally.
    2. Aggregate domain terms surfaced across Phase 1 investigations, applying the reference's criteria.
    3. If CONCEPTS.md exists: add missing terms, refine existing entries when corpus surfaced new precision. Reconcile in-scope core nouns from the declared model (backfill central but missing nouns bounded to the area in scope).
    4. If CONCEPTS.md absent and terms qualified: bootstrap and seed the area in scope only (not repo-wide).
    5. Record outcome explicitly in the report.

    Apply edits silently in all modes — no user prompt.

    Phase 5: Commit Changes¶

    After report is generated, prepare commit if files were modified.

    Headless mode defaults:

    Context Default
    On main/master Create branch (e.g., docs/refresh-auth-learnings), commit, attempt PR. Report branch name if PR fails.
    On feature branch Commit on current branch.
    Git operations fail Include recommended commands in report, continue.

    Interactive mode: Show current branch context, then ask:

    • If on main/master: Recommend create branch + PR, or commit directly, or don't commit.
    • If on feature branch, clean tree: Recommend commit to current branch, or create separate branch, or don't commit.
    • If on feature branch, dirty tree: Recommend selective staging (compound-refresh changes only) to current branch, or don't commit.

    Stage only refresh-modified files regardless.

    Commit message: Summarize what was refreshed (e.g., "update 3 stale learnings, consolidate 2 overlapping docs"), follow repo conventions, be succinct.

    Phase 5.5: Discoverability Check¶

    After refresh complete, verify instruction files surface docs/solutions/ and CONCEPTS.md (if it exists). Follow the shared Discoverability Check procedure above.

    If check produces edits: In interactive mode, apply or ask per the standard flow. In headless mode, report as "Discoverability recommendation" in the output; do not edit instruction files (headless scope is doc maintenance, not project config).
