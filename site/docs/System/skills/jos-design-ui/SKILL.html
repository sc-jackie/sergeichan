    jos-design-ui¶

    Comprehensive skill for production-grade UI: read the brief, design with taste, build against the project design doc, critique per axis, polish details, verify with screenshots.

    Slash: /jos-design-ui (optional — auto-invokes on design/redesign/polish language).

    When to invoke¶

    Load this skill before presentation-layer work when there is even ~1% chance the task changes how something looks or reads.

    Always invoke¶

    Category Examples
    Design verbs design, redesign, polish, refine, restyle, refresh, revamp, rethink
    Look & feel ugly, off, AI slop, generic, template, cleaner, hierarchy, feels better
    Surfaces screen, page, view, layout, component, hero, nav, card, form, widget
    Design system tokens, CSS variables, typography, color, spacing, theme, dark mode
    Concept full redesign, mockups, explore directions, options A/B/C, design lab
    Implementation new screen/component, *.css, design-memory / design-system edits

    Do not invoke¶

    • Backend, SQL, API, bot logic, jobs — no presentation change
    • Logic-only bugs with no visual/layout/copy ask
    • Plan-only spec review → grill-me or /planning-loop; invoke this skill when building

    Workflow (greenfield or existing)¶

    Brief Inference → Design Read → Detect mode → Design System Map → 
Read doc + tokens → Plan → Build → Heuristic snapshot → Crit → Fix → 
Update doc → Screenshot → Deploy

    For redesigns: insert Audit-First before Design System Map.

    Quality bar¶

    Hold these in addition to crit:

    1. Brief fidelity — matches user request, no hallucination
    2. Design doc match — inherits tokens, patterns, not a template
    3. One memorable anchor per screen (hero, figure, mascot, masthead)
    4. Typographic intention — deliberate scale and pairing
    5. Restraint — remove one decorative element before ship (Chanel rule)
    6. Product-native — no generic AI clusters (cream serif terracotta, dark acid, hairline broadsheet) unless brief asks
    7. Copy earns pixels — utility voice in apps; no marketing speak
    8. Screenshot gate — if it doesn't look good in the screenshot, it doesn't ship

    Design Read (before any code)¶

    Always infer, never assume. Pull only what fits the brief:

    1. Page kind — landing (SaaS / consumer / agency), portfolio, redesign, editorial, dashboard
    2. Vibe words — "minimalist", "premium", "playful", "agency-y", "trust-first", "editorial"
    3. Reference signals — URLs, screenshots, products, brands named
    4. Audience — B2B procurement, design-conscious consumer, recruiter, public-sector
    5. Brand assets — logo, color, type, photography (for redesigns: starting material, not optional)
    6. Quiet constraints — accessibility-first, regulated, kids' products, trust-first commerce

    Output: one line before code: "Reading this as: \ for \, with a \ language, leaning toward \."

    If brief is ambiguous, ask ONE clarifying question only.

    Three Dials (core configuration)¶

    After the design read, set three dials. Every layout and motion decision below is gated by these.

    • DESIGN_VARIANCE: 8 — 1 = Perfect Symmetry, 10 = Artsy Chaos
    • MOTION_INTENSITY: 6 — 1 = Static, 10 = Cinematic / Physics
    • VISUAL_DENSITY: 4 — 1 = Art Gallery / Airy, 10 = Cockpit / Packed

    Baseline: 8 / 6 / 4. Use these unless the design read overrides them.

    Dial table¶

    Brief reads as… VARIANCE MOTION DENSITY

    Design System Map (before code)¶

    For the brief, pick the right foundation:

    Brief reads as… Reach for Why
    Microsoft / enterprise SaaS @fluentui/react-components Official tokens, a11y done
    Google / Material-flavored @material/web + Material 3 Official, theme-able
    IBM-style B2B / analytics @carbon/react Official Carbon patterns
    Modern React SaaS (you own it) shadcn/ui + @radix-ui/themes You own the code, easy to customize
    Tailwind SaaS (default) Tailwind v4 + utilities Industry standard for indie builds
    Trust-first / public-sector UK govuk-frontend Legally expected
    US public-sector uswds Same

    Honesty rule: if the brief matches a real system above, install and use the official package. Do not recreate its CSS by hand.

    One system per project. Do not mix Fluent React with Carbon in the same tree.

    Planning (before code)¶

    Output briefly:

    1. Primary job — "User opens this to ___"
    2. States matrix — default, loading, empty, error, success
    3. Visual thesis — mood, material, energy (from design doc)
    4. Content plan — order and hierarchy
    5. Interaction plan — 2–3 motions from doc tokens
    6. Uniqueness check — revise any element that reads like a generic default

    Design guidance (core principles)¶

    Typography¶

    • Display + body pairing with personality; deliberate scale and weight
    • Yield to doc fonts in existing apps
    • Serif only if brief explicitly names it OR aesthetic is editorial/luxury/heritage AND you articulate why this serif fits
    • AVOID Inter as default — reach for Geist, Outfit, Cabinet Grotesk, Satoshi
    • Never use Fraunces or Instrument_Serif as defaults
    • Italic descenders: use leading-[1.1] minimum, not leading-none
    • text-wrap: balance on headings, text-wrap: pretty on body

    Color & Surfaces¶

    • CSS variables; 60/30/10 instinct: surface / structure / accent
    • Max one accent per view unless doc defines more
    • THE LILA RULE: no automatic purple/blue AI glow. Use neutral bases (Zinc/Slate/Stone) with high-contrast singular accents (Emerald, Electric Blue, Deep Rose, etc.)
    • NO pure #000000 — use off-black (zinc-950, charcoal)
    • Tint shadows to background hue, not pure black at low opacity
    • One palette per project; do not fluctuate between warm and cool grays

    Composition¶

    • Viewport as poster: whitespace, alignment, scale before chrome
    • Gestalt: proximity groups; one focal weight; figure-ground separates content from chrome
    • Cards only when the card is the interaction
    • Hero fit in viewport — headline max 2 lines, subtext max 20 words and 3-4 lines, CTA visible without scroll
    • Hero top padding cap: max pt-24 at desktop
    • Hero stack: max 4 text elements (optional eyebrow + headline + subtext + CTAs only)
    • Navigation on one line at desktop; height cap 80px max

    Motion¶

    • 2–3 intentional motions for visual-led work; use project motion tokens
    • Animate transform/opacity only; respect prefers-reduced-motion
    • MOTION MUST BE MOTIVATED — hierarchy, storytelling, feedback, state transition. Never "it looked cool."
    • Ban: window.addEventListener('scroll') — use Motion, GSAP ScrollTrigger, or IntersectionObserver
    • Sticky-Stack & Horizontal-Pan: see reference patterns below

    Fluid interaction (Apple) — core rules¶

    Full playbook with code + spring values: references/apple-design.md. Read it whenever building gesture-driven UI (drag, swipe, sheets, drawers), springs, or glass/translucent surfaces. The distilled rules:

    • Respond on pointer-down, not release. Press feedback is instant; during a drag the UI tracks the pointer 1:1 (respect the grab offset), never animating only at the end.
    • Every animation is interruptible. Animate from the current presentation value, never the target. Springs (not CSS transitions/keyframes) for anything the user can grab mid-flight.
    • Springs: critically damped by default (bounce: 0, response 0.3–0.4s). Add bounce (~0.2) only when the gesture carried momentum — a flick earns overshoot, a fade-in menu doesn't.
    • Velocity handoff + projection. On release, the spring inherits the finger's velocity, and the snap target comes from the projected resting point, not the release point.
    • Rubber-band boundaries — progressive resistance at edges, never a hard stop.
    • Spatial consistency. Enter and exit along the same path; popovers/menus scale from their trigger (transform-origin at the source), not from center.
    • Translucent chrome: backdrop-filter layers with content scrolling underneath; material weight encodes hierarchy; never stack two light glass surfaces.
    • Reduced-* trio: honor prefers-reduced-motion (cross-fade instead of slide/spring), prefers-reduced-transparency (solidify glass), prefers-contrast (defined borders).
    • Type changes shape with size: negative tracking on display text (-0.02em), ~0 on body; leading inversely tracks size.
    • Eight foundations to reason with: Purpose, Agency, Responsibility, Familiarity, Flexibility, Simplicity (not minimalism), Craft, Delight — delight is the result of the other seven, not confetti on top.

    Copy¶

    • Product voice, not design commentary
    • Active voice; consistent vocabulary through flows
    • Empty/error states invite action; errors specific, not apologetic
    • No AI clichés: "elevate", "seamless", "unleash", "next-gen", "game-changer"
    • No fake-precise numbers (92%, 4.1×, 48k) unless real data
    • NO em-dash (—) anywhere — use period, comma, colon, or line break

    Accessibility floor¶

    • Semantic HTML; WCAG AA contrast; :focus-visible on interactives
    • Icon-only buttons: aria-label (i18n where user-facing)
    • Touch ≥ doc minimum (44px typical)
    • Button contrast check (mandatory): button text readable against button background
    • Form contrast check: inputs, labels, helper text, error text all WCAG AA

    CSS discipline¶

    • Avoid specificity wars (e.g. .section vs .cta canceling padding)
    • Concentric border radius: outer radius = inner radius + padding
    • Shadows over borders for natural depth
    • Never h-screen — use min-h-[100dvh] for iOS Safari

    Audit-first approach (existing projects)¶

    Mode detection: Greenfield, Redesign-Preserve, or Redesign-Overhaul?

    Scan: Read the codebase. Framework, styling method, current patterns.

    Diagnose: Run through the audit. Generic patterns, weak points, missing states.

    Extract before changing: - Brand tokens (colors, type, radii, logo) - Information architecture (don't break slugs, nav labels, analytics tracking) - Existing design signals (DESIGN_VARIANCE, MOTION_INTENSITY reading from current site)

    Apply in priority order: 1. Font swap (biggest lift, lowest risk) 2. Color recalibration (keep brand accent, unify neutrals) 3. Hover/active states (makes interface feel alive) 4. Spacing & rhythm (section padding, vertical rhythm) 5. Replace generic components (cliché patterns) 6. Add loading, empty, error states (feels finished) 7. Polish typography scale (premium final touch)

    Criterion-resolved critique¶

    Score each axis 1–5 with evidence. Default axes:

    Checkable: brief_fidelity, token_accuracy, spatial_accuracy, copy_accuracy, scope_fidelity

    Felt: visual_hierarchy, mood_tone, typography_craft, color_harmony (fail if ≤2)

    Platform: per project doc (e.g. Rodyna telegram_fit; Newfin editorial_identity)

    Heuristic snapshot (before final crit)¶

    1. Visibility — status and next step clear?
    2. Match — language fits user world?
    3. Control — back/cancel without trap?
    4. Consistency — matches sibling screens?
    5. Error prevention — destructive obvious; empty invites action?

    Any no → fix before ship.

    Polish details checklist¶

    • [ ] Concentric border radius on nested elements
    • [ ] Icons optically centered, not geometric
    • [ ] Shadows instead of borders where appropriate
    • [ ] Enter animations split and staggered (~100ms delay)
    • [ ] Exit animations subtle (small fixed translateY, not full height)
    • [ ] Dynamic numbers use tabular-nums
    • [ ] -webkit-font-smoothing: antialiased on macOS
    • [ ] Headings use text-wrap: balance
    • [ ] Images have subtle outlines (1px with low opacity)
    • [ ] Buttons scale on press (scale-[0.96] only, never below 0.95)
    • [ ] Skip animations on page load (initial={false} on AnimatePresence)
    • [ ] No transition: all — specific properties only
    • [ ] will-change only on transform, opacity, filter
    • [ ] Interactive elements ≥ 40×40px hit area

    Hard rules & anti-patterns¶

    BANNED unless brief explicitly asks: - Purple SaaS, gradient filler, decorative 01/02/03 - Carousel without purpose, competing accents - Prompt language in UI, broken contrast, missing focus - 3-column equal feature cards (use 2-col zig-zag, asymmetric grid, or scroll) - Centered hero on every page (use split-screen, left-align, or asymmetric white-space for DESIGN_VARIANCE > 4) - Eyebrow on every section (max 1 per 3 sections) - Hero with 3+ text rows (stack vertically if text is necessary) - Fake product screenshots (div-based UI mockups) - Placeholder Lorem Ipsum or fake names ("John Doe", "Jane Smith", "Acme Corp") - Generic avatars (egg SVG, default user icons) - Section numbering eyebrows (00 / INDEX, 001 · Capabilities) - Div-based fake screenshots or decorative colored dots - Content density (cut ruthlessly; max 6-8 sections on landing) - AI copywriting clichés

    Sticky-Stack (cards stack on scroll)¶

    "use client";
import { useRef, useEffect } from "react";
import { gsap } from "gsap";
import { ScrollTrigger } from "gsap/ScrollTrigger";
import { useReducedMotion } from "motion/react";

gsap.registerPlugin(ScrollTrigger);

export function StickyStack({ cards }: { cards: React.ReactNode[] }) {
  const ref = useRef<HTMLDivElement>(null);
  const reduce = useReducedMotion();

  useEffect(() => {
    if (reduce || !ref.current) return;
    const ctx = gsap.context(() => {
      const cardEls = gsap.utils.toArray<HTMLElement>(".stack-card");
      cardEls.forEach((card, i) => {
        if (i === cardEls.length - 1) return;
        ScrollTrigger.create({
          trigger: card,
          start: "top top",
          endTrigger: cardEls[cardEls.length - 1],
          end: "top top",
          pin: true,
          pinSpacing: false,
        });
      });
    }, ref);
    return () => ctx.revert();
  }, [reduce]);

  return (
    <div ref={ref}>
      {cards.map((card, i) => (
        <div key={i} className="stack-card sticky top-0 min-h-[100dvh]">
          {card}
        </div>
      ))}
    </div>
  );
}
