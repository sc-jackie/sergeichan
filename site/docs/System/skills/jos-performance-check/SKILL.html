    jos-performance-check¶

    Output: passing benchmark run + live-audit findings table + ranked suggestions; jos-compound if the fix was non-trivial. Renamed from jos-page-load-loop 2026-07-11 — old trigger phrases still work.

    A. Benchmark — the repeatable gate¶

    1. Find the benchmark in the current repo (source of truth):
    2. Check root and miniapp/ package.json for benchmark:pages or benchmark:pages:all.
    3. Script is usually **/scripts/benchmark-page-load.ts or server/src/scripts/benchmark-page-load.ts.
    4. Newfin: npm run benchmark:pages:all — server/src/scripts/benchmark-page-load.ts
    5. Rodyna: cd miniapp && npm run benchmark:pages — miniapp/scripts/benchmark-page-load.ts
    6. New UI repo: scaffold from Jackie-OS System/templates/benchmark-page-load.md at onboarding.
    7. Baseline — run it; record failing routes and the slowest API path per screen.
    8. Same env, same BENCHMARK_TARGET_MS (default 50), same profile (web / mobile / telegram) every run.

    B. Live-app audit — what the benchmark can't see¶

    Drive the running app (project Playwright/e2e first, else browser MCP; Telegram miniapp → telegram profile). For each key screen:

    1. Network waterfall — list requests (read_network_requests / HAR). Flag: serial chains (request B starts only after A returns), duplicate calls for the same data, request count > ~6 per screen, JSON payloads > 100 KB, endpoints > 200 ms server time.
    2. Data-loading pattern — initial render blocked on fetch without a skeleton? Sequential awaits that could be Promise.all? Overfetch (fields/rows the screen never shows)? N+1 (list fetch followed by a call per item)? Unbounded lists with no pagination/virtualization?
    3. Caching — revisit the same screen: do identical GETs re-fire? Check client cache (React Query staleTime/persist), server-side cached() + bust-on-write, HTTP Cache-Control/ETag on static and semi-static responses.
    4. Asset weight — images > 200 KB or decoded larger than rendered size (serve webp/avif at display width); JS bundle per route (build analyzer): missing dynamic imports for heavy routes/libs, dependencies that dwarf their use.
    5. Render cost — only after 1–4 are clean: long tasks in the Performance panel, obvious re-render storms (state high in the tree, missing memo on hot lists).

    C. Rank & suggest¶

    Produce one table before touching code:

    | # | Finding | Screen | Cost (ms / KB) | Fix | Effort (S/M/L) |

    Order by user-felt impact, not by how interesting the fix is. If the session is review-only, stop here and present it; otherwise proceed to D on item #1.

    D. Fix loop¶

    1. Apply the smallest credible fix for the top finding — one significant change at a time.
    2. Re-measure the same way it was found (benchmark for A-findings, the specific audit check for B-findings). No eyeballing.
    3. Repeat down the table.
    4. Stop (FF 003): every page p50 ≤ target on a final full benchmark run; no regressions on previously passing routes; no serial waterfalls left on key screens; repeat visits hit cache instead of re-fetching.

    Standard levers (reach for these first)¶

    • Parallelize server-side fetches; batch N+1 into one list endpoint; Promise.all sequential awaits.
    • Cache — server cached() with bust-on-write; client staleTime matched to data volatility; Cache-Control for static.
    • Shrink payloads — select only used fields; paginate; compress images to rendered size.
    • Split bundles — dynamic-import heavy routes and libs; replace outsized deps.
    • Perceived speed — optimistic updates on mutations; skeletons only when > 150 ms; prefetch the next likely screen on idle.

    Rules¶

    • Same conditions every run — document base URL, auth bypass, and profile in the repo benchmark README.
    • New screen → add to the benchmark page spec before merge.
    • Suggest from measurements, never from vibes — every suggestion in C carries its measured cost.
    • Does not replace: ad-hoc profiling subagents; CI typecheck/test gates; jos-product-eval (functional smoke — run both before calling a sprint shipped).
