    Create and Iterate Plans¶

    Note: The current year is 2026. Use this when dating plans and searching for recent documentation.

    ce-brainstorm defines WHAT to build. jos-plan defines HOW to build it. ce-work executes the plan. A prior brainstorm is useful context but never required — this skill works from any input: a requirements doc, a bug report, a feature idea, or a rough description.

    Quality Bar. Every plan must contain: clear problem frame and scope boundary, concrete requirements traceability, repo-relative file paths, test scenarios per feature-bearing unit, decisions with rationale, no open architectural questions, existing patterns to follow. A plan is ready when an implementer can start confidently without needing the plan to write the code.

    Grill Gate. When the plan looks ready: "Plan looks ready — run grill-for-unknowns to stress-test?" Do not auto-invoke unless asked — except for significant plans (new system, architecture change, multi-day build), where the grill is the default next step. For smaller plans, just remind.

    Output Locations. Repo plans live in docs/plans/ (code repos). Jackie-OS plans live in System/plans/ or Projects/. After the plan ships in Jackie-OS-tracked work → run /wrap-up (roadmap reconcile + vault sync).

    When directly invoked, always plan. Never classify a direct invocation as "not a planning task" and abandon the workflow. If the input is unclear, ask clarifying questions or use Phase 0.4's planning bootstrap to establish enough context — but always stay in the planning workflow.

    Interaction Method¶

    When asking the user a question, use the platform's blocking question tool: AskUserQuestion in Claude Code (call ToolSearch with select:AskUserQuestion first if its schema isn't loaded), request_user_input in Codex, ask_question in Antigravity CLI, or ask_user in Pi. Fall back to numbered options in chat only when no blocking tool exists or the call errors. Never silently skip the question. Ask one question at a time; prefer single-select when natural options exist.

    Core Principles¶

    1. Use requirements as the source of truth - If ce-brainstorm produced a requirements document, planning builds from it rather than re-inventing behavior.
    2. Decisions, not code - Capture approach, boundaries, files, dependencies, risks, and test scenarios. Do not pre-write implementation code. Pseudo-code sketches or DSL grammars that communicate design are welcome when framed as directional guidance, not implementation specification.
    3. Research before structuring - Explore the codebase, institutional learnings, and external guidance when warranted before finalizing the plan.
    4. Right-size the artifact - Small work gets a compact plan. Large work gets more structure. The philosophy stays the same at every depth.
    5. Separate planning from execution discovery - Resolve planning-time questions here. Explicitly defer execution-time unknowns to implementation.
    6. Keep the plan portable - The plan should work as a living document, review artifact, or issue body without embedding tool-specific executor instructions.
    7. Carry execution posture lightly when it matters - If the request, origin document, or repo context clearly implies test-first, characterization-first, or another non-default execution posture, reflect that in the plan as a lightweight signal.
    8. Honor user-named resources - When the user names a specific resource — a CLI, MCP server, URL, file, doc link, or prior artifact — treat it as authoritative input. Discover it if unknown before assuming it's unavailable.

    Workflow¶

    Phase 0: Resume, Source, and Scope¶

    0.-1 Docs-first gate (Jackie-OS ecosystem)¶

    When the plan touches Jackie-OS or its repos (~/Jackie-OS, ~/dev/*): read ~/Jackie-OS/DOCS.md (master documentation index) before proposing new components. If a similar skill, script, worker, or connector already exists, plan an extension of it — not a parallel implementation. Note in the plan which existing components were checked.

    0.0 Resolve Output Mode¶

    Determine OUTPUT_FORMAT before any other phase. Output mode is exclusive — written as either markdown (.md) OR HTML (.html), never both. Precedence: CLI arg > config > default (md), with a hard pipeline-mode override.

    Read config. The repo root is pre-resolved at skill load; if unavailable, run git rev-parse --show-toplevel. Then read <repo-root>/.compound-engineering/config.local.yaml. If resolution fails or file doesn't exist, default to markdown.

    Resolution steps: 1. CLI arg — Scan $ARGUMENTS for a token starting with output:. Strip it, match the value case-insensitively against md and html. 2. Config — If step 1 did not resolve and config has an active (non-commented) plan_output: key, use it. Ignore commented lines. 3. Default — Otherwise OUTPUT_FORMAT=md. 4. Pipeline override — When invoked from LFG or any disable-model-invocation context, force OUTPUT_FORMAT=md regardless of steps 1-3.

    Load the format-rendering reference. When OUTPUT_FORMAT=md, read references/markdown-rendering.md. When OUTPUT_FORMAT=html, read references/html-rendering.md.

    0.1 Resume Existing Plan Work When Appropriate¶

    If the user references an existing plan file or there is an obvious recent matching plan in docs/plans/: - Read it - Confirm whether to update it in place or create a new plan - If updating, revise only the still-relevant sections

    Deepen intent. When the user says "deepen the plan", "deepen my plan", or similar, the target is a plan in docs/plans/, not a requirements document. If a path is provided, verify it is actually a plan. If the match is not obvious, confirm with the user.

    Once the plan is identified and appears complete: - .html plan: short-circuit to Phase 5.3 (Confidence Check) in interactive mode. - .md plan WITH YAML frontmatter: short-circuit to Phase 5.3 in interactive mode. - .md plan WITHOUT YAML frontmatter (non-software plans): route to references/universal-planning.md instead.

    Resume preserves the existing artifact's format, except pipeline mode always forces .md (downstream automation expects markdown).

    0.1a Recognize Approach-Altitude Requests¶

    When the user asks for the approach itself — "plan for a plan", "plan the approach", "plan how you'll do X", "don't do it yet -- just plan how you'd approach it" — enter approach altitude and hold at the approach. Do NOT begin the deliverable.

    Proactive (rare, conservative). Offer an approach-plan only when both are clearly high: - Method uncertainty — the core approach is genuinely unsettled with competing methodologies yielding different deliverables. - Cost of getting it wrong — the deliverable is expensive to produce and a wrong approach wastes real effort.

    If either is low, stay silent and plan normally. When the offer does fire, it is a single dismissible line naming the specific signal — never a blocking question.

    On entry (explicit, or an accepted offer), read references/approach-altitude.md and follow it. Otherwise continue to Phase 0.1b unchanged.

    0.1b Classify Task Domain¶

    If the task asks to build, modify, refactor, deploy, or architect software (code, schemas, infrastructure), continue to Phase 0.2.

    Otherwise, read references/universal-planning.md and follow that workflow instead. Skip all subsequent phases.

    0.2 Find Upstream Requirements Document¶

    Before asking planning questions, search docs/brainstorms/ for files matching *-requirements.md or *-requirements.html.

    Relevance criteria: A requirements document is relevant if: - The topic semantically matches the feature description - It was created within the last 30 days (use judgment to override if clearly still relevant) - It appears to cover the same user problem or scope

    If multiple sources match, ask which one to use. If a single match is found, use it as the origin document.

    0.3 Use the Source Document as Primary Input¶

    If a relevant requirements document exists: 1. Read it thoroughly 2. Announce that it will serve as the origin document for planning 3. Carry forward: problem frame, actors (A-IDs), Key Flows (F-IDs), Acceptance Examples (AE-IDs), requirements, success criteria, scope boundaries, key decisions and rationale, dependencies or assumptions, outstanding questions 4. Use the source document as the primary input to planning and research 5. Reference important carried-forward decisions in the plan with (see origin: <source-path>) 6. Do not silently omit source content — if the origin document discussed it, the plan must address it even if briefly

    If no relevant requirements document exists, planning may proceed from the user's request directly.

    0.4 Planning Bootstrap (No Requirements Doc or Unclear Input)¶

    If no relevant requirements document exists, or the input needs more structure: - Assess whether the request is already clear enough for direct technical planning - If ambiguity is mainly product framing, user behavior, or scope definition, recommend ce-brainstorm as a suggestion — but always offer to continue planning here as well - If the user wants to continue here, run the planning bootstrap below

    The planning bootstrap should establish: problem frame, intended behavior, scope boundaries and obvious non-goals, success criteria, blocking questions or assumptions.

    Keep this bootstrap brief. It exists to preserve direct-entry convenience, not to replace a full brainstorm.

    If the bootstrap uncovers major unresolved product questions, recommend ce-brainstorm again. If the user still wants to continue, require explicit assumptions before proceeding.

    Bug-shaped prompt. If the user describes broken behavior — "fix the bug where X", error message, regression — surface ce-debug as a route-out option alongside continuing with planning when the bug surface is reachable (in cwd OR named repo found locally). Stay in ce-plan silently when the named code can't be found locally — paper-planning is the only useful output.

    Clear task ready to execute. When the root cause is obvious and the fix is clear with no architectural decisions, suggest ce-work as a faster alternative alongside continuing with planning. The user decides.

    0.5 Classify Outstanding Questions Before Planning¶

    If the origin document contains Resolve Before Planning or similar blocking questions: - Review each one before proceeding - Reclassify it into planning-owned work only if it is actually a technical, architectural, or research question - Keep it as a blocker if it would change product behavior, scope, or success criteria

    If true product blockers remain, surface them clearly and ask whether to: 1. Resume ce-brainstorm to resolve them 2. Convert them into explicit assumptions or decisions and continue

    Do not continue planning while true blockers remain unresolved.

    0.6 Assess Plan Depth¶

    Classify the work into one of these plan depths: - Lightweight — small, well-bounded, low ambiguity - Standard — normal feature or bounded refactor with some technical decisions to document - Deep — cross-cutting, strategic, high-risk, or highly ambiguous implementation work

    If depth is unclear, ask one targeted question and then continue.

    0.7 Solo-Mode Scoping Synthesis¶

    Surface call-outs to the user — the specific forks in scope or approach where user input materially changes the plan — so scope can be corrected before Phase 1 research is spent. This phase fires only in solo invocation — when Phase 0.2 found no upstream brainstorm doc AND Phase 0.4 stayed in this skill AND Phase 0.5 cleared AND not on Phase 0.1 fast paths (resume normal, deepen-intent).

    Read references/synthesis-summary.md before composing the scoping synthesis. It carries the affirmability test, keep-test criteria, detail test, summary shape budgets, granularity rules, anti-patterns, revision-vs-confirmation discipline, and headless-mode routing.

    Required gate output — do not skip; silent proceeding is not allowed. Compose an internal three-bucket scope draft (Stated / Inferred / Out of scope) and derive call-outs (specific forks where user input materially changes the plan). Emit one of the two templates below in chat before continuing to Phase 1.

    Synthesis is pre-plan-write. The agent does NOT yet know how plan-write will sequence the work. Do not claim PR count, commit/branch shape, effort estimates, Implementation Unit boundaries, or exact file paths. The synthesis surfaces decisions knowable at THIS point; plan-write produces the rest.

    Summary shape: prose, bullets, or mix; tier budgets are ceilings, not targets (Lightweight 1-3 lines; Standard up to 3-5 lines or 2-4 bullets; Deep up to 4-6 lines or 3-6 bullets).

    Do NOT enumerate the touch surface. File paths, module names, directory introductions belong in the plan body (Implementation Units), not the synthesis.

    Tier guard on auto-proceed: auto-proceed (announce without waiting for confirmation) fires only when plan depth is Lightweight AND zero call-outs survive. Standard and Deep plans always fire the confirmation gate, even with zero call-outs.

    Confirmation template (Standard/Deep or any tier with call-outs):

    Based on your request and our brief discussion, here's the scope I'm proposing to plan against:

[scope claim — what the plan will target, what it will not; affirm-or-redirect level]

**Call outs:**
- [decision-level fork in 1-2 lines]

Confirm and I'll proceed to research. (You can also redirect to /ce-brainstorm if this is bigger than you initially thought.)

    Wait for user confirmation before continuing to Phase 1.

    Auto-proceed template (Lightweight with zero call-outs only):

    Planning: [1-3 line scope claim]

No open decisions to weigh in on — proceeding to research. Interrupt if I have the scope wrong.

    Then continue to Phase 1 without a blocking question.

    Phase 1: Gather Context¶

    All specialist research prompts used in this phase are under references/agents/. When dispatching, read the matching file and seed a generic subagent with that prompt content plus task-specific context.

    1.1 Local Research (Always Runs)¶

    Prepare a concise planning context summary to pass to research agents. Run these agents in parallel: - references/agents/repo-research-analyst.md — scope: technology, architecture, patterns - references/agents/learnings-researcher.md — institutional learnings

    Collect: technology stack and versions, architectural patterns and conventions, implementation patterns and relevant files, institutional learnings from docs/solutions/, product strategy context when STRATEGY.md is present.

    Agent-native planning triage (conditional) — Dispatch a generic subagent with references/agents/agent-native-planning-strategist.md in parallel when the request, origin document, or repo research indicates agent, assistant, chat, workflow automation, MCP, plugin, skill, tool registry, prompt, or autonomous-loop work.

    1.1b Detect Execution Posture Signals¶

    Decide whether the plan should carry a lightweight execution posture signal (test-first, characterization-first, etc.) based on explicit user requests, origin document calls, or local research showing legacy or weakly-tested areas. When the signal is clear, carry it forward silently in relevant implementation units. Ask the user only if the posture would materially change sequencing or risk.

    1.2 Decide on External Research¶

    Stage 1 — Explicit request takes precedence. If the user prompt or origin requirements explicitly ask for external input (best practices, competitor/prior-art comparison, alternatives, market scan, naming a specific external technology to consult), external research is required.

    Stage 2 — Classify the research intent: implementation-guidance (how to build it well), landscape/option-discovery (what options or prior art exist), or mixed.

    Stage 3 — Implicit signals: user familiarity, user intent, topic risk (security, payments, external APIs warrant more caution), uncertainty level.

    Always lean toward external research when: - The topic is high-risk: security, payments, privacy, external APIs, migrations, compliance - The codebase lacks relevant local patterns (fewer than 3 direct examples) - Local patterns exist for an adjacent domain but not the exact one - The user is exploring unfamiliar territory - The technology scan found the relevant layer absent or thin

    Skip external research when (only when Stage 1 found no explicit request): - The codebase already shows a strong local pattern (multiple direct examples, recently touched, following current conventions) - The user already knows the intended shape - Additional external context would add little practical value

    Announce the decision briefly before continuing.

    1.3 External Research (Conditional)¶

    Based on Phase 1.2, dispatch by the intent classified in Stage 2, using the platform's subagent primitive where available: - Implementation-guidance — run in parallel: references/agents/best-practices-researcher.md and references/agents/framework-docs-researcher.md - Landscape / option-discovery — references/agents/web-researcher.md - Mixed — sequential: web-researcher first to map the landscape, then framework-docs-researcher and/or best-practices-researcher against the shortlist

    1.4 Consolidate Research¶

    Summarize relevant codebase patterns and file paths, institutional learnings, organizational context from Slack conversations if gathered, external references and best practices, related issues/PRs, and any constraints that should shape the plan.

    Land external findings in decisions, not an appendix. Any external research that ran must surface where it changes a choice — Key Technical Decisions rationale, Alternatives, Risks, or Sources & Research — not as a detached list.

    Mark whether external research was load-bearing — did external findings materially shape a KTD, Alternative, Scope boundary, or Risk? Phase 5.3.2 reads this flag.

    1.4b Reclassify Depth When Research Reveals External Contract Surfaces¶

    If the current classification is Lightweight and Phase 1 found that the work touches environment variables, exported public APIs, CI/CD configuration, shared types imported by downstream consumers, or documentation referenced by external URLs, reclassify to Standard. Announce briefly: "Reclassifying to Standard — this change touches [external contract surface] with external consumers."

    1.5 Flow and Edge-Case Analysis (Conditional)¶

    For Standard or Deep plans, run references/agents/spec-flow-analyzer.md to identify missing edge cases, state transitions, or handoff gaps. Use the output to tighten requirements trace or verification strategy. Add only the flow details that materially improve the plan.

    Phase 2: Resolve Planning Questions¶

    Build a planning question list from deferred questions in the origin document, gaps discovered in repo or external research, and technical decisions required to produce a useful plan.

    For each question, decide whether it should be resolved during planning (the answer is knowable from repo context, documentation, or user choice) or deferred to implementation (the answer depends on code changes, runtime behavior, or execution-time discovery).

    Ask the user only when the answer materially affects architecture, scope, sequencing, or risk and cannot be responsibly inferred. Do not run tests, build the app, or probe runtime behavior in this phase.

    Phase 3: Structure the Plan¶

    3.1 Title and File Naming¶

    • Draft a clear, searchable title using conventional format such as feat: Add user authentication or fix: Prevent checkout double-submit
    • Determine the plan type: feat, fix, or refactor
    • Build the filename following the repository convention: docs/plans/YYYY-MM-DD-NNN-<type>-<descriptive-name>-plan.md
    • Create docs/plans/ if it does not exist
    • Check existing files for today's date to determine the next sequence number (zero-padded to 3 digits, starting at 001)
    • Keep the descriptive name concise (3-5 words) and kebab-cased

    3.2 Stakeholder and Impact Awareness¶

    For Standard or Deep plans, briefly consider who is affected by this change — end users, developers, operations, other teams — and how that should shape the plan.

    3.3 Break Work into Implementation Units¶

    Break the work into logical implementation units. Each unit should represent one meaningful change that an implementer could typically land as an atomic commit. Good units are focused on one component, behavior, or integration seam, touch a small cluster of related files, ordered by dependency, and concrete enough for execution.

    Each unit carries a stable plan-local U-ID assigned in Phase 3.5 (U1, U2, …). U-IDs survive reordering, splitting, and deletion: new units take the next unused number, gaps are fine, existing IDs are never renumbered.

    3.4 High-Level Technical Design¶

    When the plan's technical approach has shape that prose alone doesn't carry well — architecture across components, sequencing across processes, state machines, lifecycles — include a High-Level Technical Design section. See references/plan-sections.md for the section catalog and "include when material" criterion.

    When the plan's approach is a one-paragraph pattern application that prose conveys directly, skip the section.

    3.4b Output Structure (Optional)¶

    For greenfield plans that create a new directory structure (new plugin, service, package, or module), include an ## Output Structure section with a file tree when: - The plan creates 3+ new files in a new directory hierarchy - The directory layout itself is a meaningful design decision

    3.5 Define Each Implementation Unit¶

    Each unit is a level-3 heading with format ### U1. [Name]. Number sequentially starting at U1. Do not use bulleted list items or checkboxes.

    Stability rule. Once assigned, a U-ID is never renumbered. Reordering leaves IDs in place. Splitting keeps the original U-ID on the original concept and assigns the next unused number to the new unit.

    For each unit, include: - Goal — what this unit accomplishes - Requirements — which requirements it advances (cite R-IDs, A/F/AE IDs when origin supplies them) - Dependencies — what must exist first (cite by U-ID) - Files — repo-relative file paths to create, modify, or test (never absolute paths) - Approach — key decisions, data flow, component boundaries, or integration notes - Execution note — optional, only when the unit benefits from test-first or characterization-first posture - Patterns to follow — existing code or conventions to mirror - Test scenarios — enumerate the specific test cases: happy path behaviors, edge cases, error and failure paths, integration scenarios. Each scenario should name the input, action, and expected outcome. When a test scenario directly enforces an origin Acceptance Example, prefix it with Covers AE<N>. For units with no behavioral change (pure config, scaffolding, styling), use Test expectation: none -- [reason]. - Verification — how an implementer should know the unit is complete

    Every feature-bearing unit should include the test file path in **Files:**.

    3.6 Keep Planning-Time and Implementation-Time Unknowns Separate¶

    If something is important but not knowable yet, record it explicitly under deferred implementation notes rather than pretending to resolve it.

    3.7 Anti-Expansion: Tangential Cleanup and Scope Creep Go to Deferred¶

    When research surfaces an adjacent refactor, a "while we're here" cleanup, or a scope-adjacent nice-to-have, route it to the ### Deferred to Follow-Up Work subsection in Scope Boundaries, not into active Implementation Units.

    Phase 4: Write the Plan¶

    NEVER CODE during this skill. Research, decide, and write the plan — do not start implementation.

    4.1 Plan Depth Guidance¶

    Lightweight — Keep compact, usually 2-4 implementation units, omit optional sections that add little value.

    Standard — Use the full core template, omitting optional sections that add no value for this particular work. Usually 3-6 implementation units. Include risks, deferred questions, and system-wide impact when relevant.

    Deep — Use the full core template plus optional analysis sections where warranted. Usually 4-8 implementation units. Group units into phases when that improves clarity. Include alternatives considered, documentation impacts, and deeper risk treatment.

    4.1b Optional Deep Plan Extensions¶

    For sufficiently large or risky work, add sections that genuinely help: - Alternative Approaches Considered - Success Metrics - Dependencies / Prerequisites - Risk Analysis & Mitigation - Phased Delivery - Documentation Plan - Operational / Rollout Notes - Future Considerations

    Do not add as boilerplate. Include only when they improve execution quality or stakeholder alignment.

    4.2 Section Contract and Rendering¶

    Compose the plan using two paired references: - references/plan-sections.md — the section contract - The format-rendering reference loaded at Phase 0.0 (markdown-rendering.md OR html-rendering.md)

    Omit "include when material" sections that don't carry information for this specific plan.

    4.3 Planning Rules¶

    • Horizontal rules (---) between top-level sections in Standard and Deep plans for scannability. Omit for Lightweight plans.
    • All file paths must be repo-relative — never use absolute paths
    • Prefer path plus class/component references over brittle line numbers
    • Do not include implementation code — no imports, exact method signatures, or framework-specific syntax
    • Pseudo-code sketches and DSL grammars are allowed in High-Level Technical Design when framed as directional guidance
    • Mermaid diagrams are encouraged when they clarify flows or relationships
    • Do not include git commands, commit messages, or exact test command recipes
    • Do not expand implementation units into micro-step instructions
    • Do not pretend an execution-time question is settled just to make the plan look complete

    Phase 5: Final Review, Write File, and Handoff¶

    5.1 Review Before Writing¶

    Before finalizing, check: - The plan does not invent product behavior that should have been defined in ce-brainstorm - Every major decision is grounded in the origin document or research - Each implementation unit is concrete, dependency-ordered, and implementation-ready - Test scenarios name specific inputs, actions, and expected outcomes - Deferred items are explicit and not hidden as fake certainty - U-IDs are unique within the plan and follow the stability rule - If the plan originated from a requirements document, re-read that document and verify scope boundaries, success criteria, and blocking questions match

    5.1.5 Brainstorm-Sourced Scoping Synthesis¶

    Surface plan-time call-outs before Phase 5.2 commits the plan to disk. Fires only when the plan was sourced from an upstream brainstorm doc AND not on Phase 0.1 fast paths (resume normal, deepen-intent).

    Read references/synthesis-summary.md before composing. It carries the affirmability test, keep-test criteria, detail test, summary shape budgets, and headless-mode routing.

    Required gate output — do not skip. Compose an internal three-bucket scope draft and derive call-outs. Emit one of the two literal templates in chat before continuing to Phase 5.2.

    Synthesis is pre-plan-write. The agent does NOT yet know how plan-write will sequence the work. Do not claim PR count, commit/branch shape, effort estimates, Implementation Unit boundaries, or exact file paths.

    Summary shape: two paragraphs. 1) Brainstorm-scope restatement (1-2 sentences). 2) Plan-specific scoping decisions (prose or bullets; tier budgets are ceilings, not targets).

    Confirmation template (Standard/Deep or with call-outs):

    The brainstorm scopes [1-2 sentence restatement in the brainstorm's vocabulary].

This plan [plan-specific scoping decisions: full-brainstorm coverage vs. narrowed subset; adjacent refactors in or out; test scope].

**Call outs:**
- [plan-time fork in 1-2 lines]

Confirm and I'll write the plan next.

    Wait for user confirmation before continuing to Phase 5.2.

    Auto-proceed template (Lightweight with zero call-outs only):

    Planning [brief brainstorm-scope restatement] — [plan-specific shape in one clause].

No open decisions to weigh in on — proceeding to plan-write. Interrupt if I have the scope wrong.

    Then continue to Phase 5.2 without a blocking question.

    5.2 Write Plan File¶

    REQUIRED: Write the plan file to disk before presenting any options.

    Use the Write tool to save the complete plan to:

    docs/plans/YYYY-MM-DD-NNN-<type>-<descriptive-name>-plan.<md|html>

    Extension follows OUTPUT_FORMAT — .md when markdown, .html when HTML. Sequence number NNN is derived from existing plan files in docs/plans/ regardless of extension.

    Compose using references/plan-sections.md and the format-specific principles from the rendering reference loaded at Phase 0.0.

    Write tight. Hold every kept section to the prose-economy discipline: one idea per sentence, a requirement or unit is intent plus at most one qualifier, defer forks to Open Questions rather than specifying both arms. Before declaring the plan written, could the implementer find a contradiction in each section in one pass?

    Confirm (use absolute path):

    Plan written to <absolute path to plan>

    CONCEPTS.md gap-fill (only if the file already exists): If the plan body uses a domain term whose definition is missing from CONCEPTS.md, add the entry — domain entities, named processes, and status concepts with project-specific meaning only. Follow the format set by existing entries. Apply silently. Skip entirely if CONCEPTS.md does not exist.

    5.3 Confidence Check and Deepening¶

    After writing the plan file, automatically evaluate whether the plan needs strengthening.

    Two deepening modes: - Auto mode (default during plan generation): Runs without asking. Sub-agent findings are synthesized directly into the plan. - Interactive mode (activated by the re-deepen fast path in Phase 0.1): The user explicitly asked to deepen. Sub-agent findings are presented for review before integration.

    5.3.1 Classify Plan Depth and Topic Risk¶

    Determine the plan depth from the document. Build a risk profile from signals like: authentication/authorization, payments/billing, data migrations/backfills, external APIs, privacy/compliance, cross-interface parity, significant rollout/monitoring/operational concerns.

    5.3.2 Gate: Decide Whether to Deepen¶
    • Lightweight plans usually do not need deepening unless they are high-risk
    • Standard plans often benefit when important sections still look thin
    • Deep or high-risk plans often benefit from a targeted second pass
    • Thin local grounding override: If Phase 1.2 triggered external research because local patterns were thin, always proceed to scoring
    • Load-bearing external research override: If Phase 1.4 marked external research as load-bearing, always proceed to scoring

    If the plan already appears sufficiently grounded and neither override applies, report "Confidence check passed — no sections need strengthening", then load references/plan-handoff.md and execute 5.3.8 → 5.3.9 → 5.4 in sequence.
